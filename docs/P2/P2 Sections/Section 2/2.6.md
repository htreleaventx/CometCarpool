# 2.6 Feasibility summary

| Feasibility gate | Verdict | Evidence behind the verdict |
| :--- | :--- | :--- |
| Technical | Feasible | The team has selected React/TypeScript for the frontend, Spring Boot for the backend, and PostgreSQL for the database. The chosen layered (N-Tier) architecture separates presentation, business logic, and data storage. These technologies support the system's core requirements, although frontend development experience and validation of performance, security, and reliability remain important technical considerations. |
| Operational | Feasible, pending user validation | The existing Ride Sharing section in the UTD application demonstrates that students already have a way to coordinate shared transportation. Comet Carpool would provide a more structured process for offering rides, searching for transportation, and managing ride requests. As identified in Section 2.5 (A1–A3), its effectiveness depends on sufficient student participation, reliable university email verification, and the ability to coordinate rides without real-time tracking or automatic route optimization. Actual user interest remains to be validated. |
| Schedule | Feasible | The project milestones remain P1 (October 18), P2 (November 8), and P3 (December 9). The team uses GitHub Issues, assigned responsibilities, and pull requests to coordinate work. While the technical stack and architectural style have been selected, some architecture documentation, decision records, and prototype evidence still require completion or integration into the main branch. The remaining work must be coordinated carefully to meet the established deadlines. |
| Economic / resource | Feasible with current resources, pending deployment confirmation | The team has access to personal computers, a shared GitHub repository, and open-source development technologies, including React, Spring Boot, and PostgreSQL. The core functionality does not require paid payment-processing or GPS-tracking services. However, hosting, database deployment, and email verification may introduce additional costs or configuration requirements that must be evaluated before deployment. |
