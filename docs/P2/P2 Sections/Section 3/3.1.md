# 3.1 Functional requirements

| **ID** | **Requirement — one “shall” sentence** | **Priority** | **Source** | **Acceptance criterion** |
| :--- | :--- | :--- | :--- | :--- |
| FR-01 | The system shall allow a UTD student to create a CometCarpool user account | MUST | S1, S2, R2 | A tester can create a new account using valid student information and successfully access the system |
| FR-02 | The system shall allow a user to update their account info | SHOULD | S1, S2, R2 | A tester can edit an allowed profile field, save it, and see the value updated after refreshing the profile |
| FR-03 | The system shall allow a driver to post an available ride | MUST | S1, R2, R3 | A tester acting as a driver can create a ride post and see it listed as available |
| FR-04 | The system shall allow a rider to post a ride request | MUST | S2, R2, R3 | A tester acting as a rider can create a ride request and see it listed for drivers |
| FR-05 | The system shall allow users to specify a pickup location, destination, date, and time for a ride or ride request. | MUST | S1, S2, R2 | A tester can enter all trip details and confirm they appear correctly on the posting |
| FR-06 | The system shall allow users to search for available rides and ride requests. | MUST | S1, S2, R2 | A tester can search using specified criteria and view available ride or ride-request postings that match those criteria. |
| FR-07 | The system shall allow drivers to record the days and times they are regularly available to drive | SHOULD | S1, R2 | A driver can save recurring availability for select days/times and view it after saving |
| FR-08 | The system shall allow riders to record the days and times they regularly need transportation | SHOULD | S2, R2 | A rider can save recurring transportation needs for select days/times and view it after saving |
| FR-09 | The system shall allow users to identify riders or drivers with compatible recurring schedules | SHOULD | S1, S2, R2 | A tester can enter compatible schedules for two users and confirm that the system identifies them as a potential match |
| FR-10 | The system shall allow a rider and driver to exchange messages through an In App Messaging system | MUST | S1, S2, R2 | Two test accounts, representing a rider and a driver, can exchange messages through the in-app messaging system, and each account can view messages sent by the other. |
| FR-11 | The system shall allow a user to cancel a posted ride or ride request | MUST | S1, S2, R2 | A tester can cancel an active posting and confirm that it is no longer shown as available |
| FR-12 | The system shall allow riders and drivers to indicate an agreement to split travel costs | COULD | S1, S2, R2 | A tester can indicate that travel costs will be shared and see that agreement associated with the ride |
| FR-13 | The system shall allow riders and drivers to submit a rating and review for one another | SHOULD | S1, S2, R2 | After a completed ride, a tester acting as either a rider or driver can submit a rating and written review of the other participant. |
| FR-14 | The system shall allow a user to report another user, review, or ride related issues | MUST | S1, S2, S3, R2 | A tester can submit a report about a user, review, or ride-related issue, include a description, and receive confirmation that the report was submitted. |
| FR-15 |The system shall allow users to create ride postings with destinations on the UTD campus or in the surrounding Dallas area. | MUST | S1, S2, R2 | A tester can create one ride to UTD and another ride to Dallas destination and save both successfully |


Functional Requirements Review — P2

Reviewed functional requirements FR-01 through FR-15 for clarity, consistency, and testability.

Minor wording and acceptance-criterion corrections were proposed for FR-05, FR-06, FR-10, FR-13, FR-14, and FR-15.

All existing requirement IDs and priorities were preserved. No new functional requirements were introduced.

The reviewed requirements remain consistent with the project's approved scope and P2 use case analysis.
