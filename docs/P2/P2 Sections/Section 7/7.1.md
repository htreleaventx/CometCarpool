# 7.1 Architecture Decision Records

## Overview

This section documents the major architectural decisions made during the design of the Comet Carpool System.

Each Architecture Decision Record (ADR) explains the context of a decision, the alternatives considered, the selected approach, and the consequences of that choice.

At least three ADRs are required. ADR-01 documents the architectural style selected in Section 6.2.

## ADR-01 — Adopt Layered (N-Tier) Architecture 

| Field | Description |
| :--- | :--- |
| **Status** | Accepted |
| **Date and Owner** | October 27, 2026 - Hunter Treleaven |
| **Context (Drivers)** | System requires separation of frontend, backend, and database responsibilities while we support QAS-01/03/04/05/06 |
| **Options Considered** | Layered (N-Tier), Client-Server, Model-View-Controller, Repository, and Event-Driven architectures |
| **Decision** | Adopt Layered (N-Tier) architecture using React/TypeScript, Spring Boot, and PostgreSQL |
| **Consequences** | Improves maintainability, separation of concerns and security. Accepts additional communication between layers and coordination when changes effect multiple components | 
| **Evidence** | Section 6.2 and 6.3 |
| **Related** | QAS-01/03/04/05/06 |

### Context

Comet Carpool requires an architecture that separates the frontend, backend, and database responsibilities while maintaining security, performance, reliability and usability. The decision was influenced by QAS-01/03/04/05/06.

The architecture must support core use cases including UC-02/03/04.

The system has to follow constraints CON-01/02/03/04

### Options Considered

Document at least two architectural alternatives that the team considered.

| Option | Advantages | Disadvantages |
| :--- | :--- | :--- |
| Layered (N-Tier) | Separates the frontend, backend, and database responsibilities; supports maintainability, security, and usability | Changes affecting multiple layers require coordination; the centralized backend may become a performance bottleneck |
| Client-Server | Centralizes application state and database access while allowing the React frontend to communicate with the Spring Boot backend | The server can become a single point of failure and does not independently organize the backend into separate layers | 
| Model-View-Controller | Separates presentation, input handling, and application state | Introduces additional organizational overhead, and business logic may become mixed into controllers |
| Repository | Allows components to share information through centralized storage, supporting data consistency | The shared repository can become a single point of failure, and schema changes may affect dependent components |
| Event-Driven | Supports asynchronous communication and may improve scalability for messaging and notifications | Introduces additional implementation complexity for the project's scope | 

### Decision

The team selected the Layered (N-Tier) architecture because it separates the React/TypeScript frontend, Spring Boot backend, domain model, and PostgreSQL database into distinct layers. This supports our security, performance, reliability, and usability requirements while keeping the system organized and maintainable.

### Consequences

The selected architecture provides separation of concerns, improved maintainability, and security through defined responsibilities between layers. It supports QAS-01/03/04/05/06 by organizing request processing, protecting sensitive information, and separating the user interface from backend operations.

However, the team accepts additional communication between layers, coordination when changes affect multiple components, and the possibility of the centralized backend becoming a performance bottleneck.

### Evidence

Section 6.2 documents the architectural alternatives considered and explains why Layered (N-Tier) was selected. Section 6.3 provides the UML component diagram showing the separation of responsibilities between the frontend, backend, domain model, and database.

These documents support the architectural design decision. Performance and reliability targets have not yet been demonstrated by measured results in the supplied documentation.

## ADR-02 — Backend Authentication and Authorization

| Field | Description |
| :--- | :--- |
| **Status** | ACcepted |
| **Date and Owner** | November 3, 2026 - Hunter Treleaven |
| **Context (Drivers)** | CometCarpool requires secure authentication and authorization to protect users accounts and restricted features. Supported by QAS-05 and CON-01 |
| **Options Considered** | Spring Security with JWT, server-side session authentication, and frontend only access checks |
| **Decision** | Uses Spring Security with JWT to manage authentication and authorization through the Spring Boot backend |
| **Consequences** | Improves security by validating access on the backend. Accepts additional complexity involving JWT management, protected API endpoints, and authentication testing |
| **Evidence** | Section 6.1, 6.3, and exisiting Spring Boot authentication implementation |
| **Related** | QAS-05, CON-01, ADR-01 |

### Context

Comet Carpool requires authentication and authorization to protect user accounts, private information, messaging, reviews, reports, and recurring schedules. QAS-05 requires the system to deny access to unauthenticated users during unauthorized access tests.

CON-01 also requires account registration and system access to be restricted to authorized members of the UTD community.

### Options Considered

| Option | Advantages | Disadvantages |
| :--- | :--- | :--- |
| Spring Security with JWT | Provides backend authentication and supports protected REST API endpoints | Requires token management, secure storage considerations, and additional testing |
| Server-Side Session Authentication | Allows the backend to manage sessions and revoke access centrally | Requires session management and additional considerations for scaling |
| Frontend-Only Access Checks | Simple to implement for controlling which pages are displayed | Does not securely protect backend resources because client-side checks can be bypassed |

### Decision

The proposed decision is to use Spring Security with JWT for authentication and authorization within the Spring Boot backend.

Authentication will be managed by the Authentication Service, while protected REST endpoints will verify whether users are authorized to access restricted system functionality. The React frontend will communicate with the backend through the defined REST API.

### Consequences

This approach supports QAS-05 by enforcing authentication and authorization at the backend rather than relying on frontend access checks. It also supports the selected Layered (N-Tier) architecture by keeping security responsibilities within the application layer.

The team accepts additional complexity involving token handling, authentication configuration, protected endpoint management, and security testing.

Section 6.3 identifies the Authentication Service and its AuthAPI interface.

## ADR-03 — Decision 

| Field | Description |
| :--- | :--- |
| **Status** | Accepted |
| **Date and Owner** | November 3, 2026 - Hunter Treleaven |
| **Context (Drivers)** | Comet Carpool requires reliable storage and retrieval of user accounts, ride postings, ride requests, recurring schedules, messages, reviews, and reports while supporting QAS-01/02/03 |
| **Options Considered** | PostgreSQL with Spring Data JPA/Hibernate, direct SQL/JDBC access, and NoSQL database storage (alternatives require team confirmation) |
| **Decision** | Use PostgreSQL for centralized data storage with Spring Data JPA/Hibernate to manage persistence through the Spring Boot backend |
| **Consequences** | Supports data consistency, reliability, and maintainability through centralized persistence. Accepts database dependency, additional ORM configuration, and potential performance bottlenecks |
| **Evidence** | Sections 6.1, 6.2, and 6.3 and existing PostgreSQL and Spring Boot integration |
| **Related** | QAS-01/02/03, UC-02/03/04, ADR-01 |

### Context

Comet Carpool requires a database to store and retrieve information related to users, rides, ride requests, recurring schedules, messages, reviews, and reports. The system must support QAS-01 (Performance), QAS-02 (Message Delivery Performance), and QAS-03 (Reliability).

The database must also support core use cases UC-02/03/04, which involve creating ride postings, searching for available rides, submitting ride requests, and managing recurring schedules.

The selected database approach should work with the Spring Boot backend while keeping data access separate from the frontend.

### Options Considered

| Option | Advantages | Disadvantages |
| :--- | :--- | :--- |
| PostgreSQL with Spring Data JPA/Hibernate | Provides structured relational storage, supports transactions, and integrates with the Spring Boot backend | Requires database configuration, entity mappings, and ORM management |
| Direct SQL/JDBC Access | Provides direct control over SQL queries and database operations | Requires more manual query handling, connection management, and persistence code |
| NoSQL Database | Can provide flexible document storage and accommodate changing data structures | May introduce additional complexity when managing relationships between users, rides, ride requests, and recurring schedules |

### Decision

The proposed decision is to use PostgreSQL with Spring Data JPA/Hibernate for centralized database persistence.

PostgreSQL will store the application's data, while Spring Data JPA/Hibernate will manage persistence through the Carpool Repository component within the Spring Boot backend.

This approach supports the Layered (N-Tier) architecture selected in ADR-01 by separating application responsibilities from database access.

### Consequences

Using PostgreSQL with Spring Data JPA/Hibernate provides structured data storage, centralized persistence, and separation of concerns between application logic and data access.

This approach supports QAS-01/02/03 by providing a foundation for ride searches, message storage and retrieval, and reliable database operations.

However, the team accepts additional configuration and maintenance of the database and ORM mappings. The centralized database may become a performance bottleneck or single point of failure if additional availability measures are not implemented.

### Evidence

Section 6.1 defines QAS-01/02/03, which establish measurable performance, message delivery, and reliability requirements.

Section 6.2 documents the selected Layered (N-Tier) architecture and discusses centralized data storage as an architectural consideration.

Section 6.3 identifies the Carpool Repository and PostgreSQL Database components and their responsibilities.

The project also has an existing Spring Boot and PostgreSQL integration. However, the provided documentation does not yet establish measured results proving that the database implementation meets the QAS performance and reliability targets.
