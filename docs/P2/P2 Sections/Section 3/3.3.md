# 3.3 Constraint requirements

| **ID** | **Constraint — one sentence** | **Source** | **Why it cannot be negotiated** |
| :--- | :--- | :--- | :--- |
| CON-01 | The system shall restrict account creation and system access to members of the UTD community | S1, S2, R2 | CometCarpool is specifically intended for UTD students, so unrestricted public access would change our defined scope and target users |
| CON-02 | The system shall not process, store, or transfer payments between riders and drivers | S1, S2, R2 | Payment processing was excluded from the project scope because it introduces additional finances, security, and legal responsibilities |
| CON-03 | The system shall not provide real time GPS tracking of riders or drivers | S1, S2, R2 | Real time tracking was excluded because of privacy, safety, and implementation concerns |
| CON-04 | The system shall not automatically import a students official class schedule | S1, S2, R2 | Accessing official class schedules would require external systems and permissions that are outside the project scope |

## Constraint Review

The original constraint requirements from P1 were reviewed against Section 2.4, the approved project scope, 
and the architectural decisions documented in P2.

- CON-01: Remains consistent with the restriction of system access to verified members of the UTD community.
- CON-02: Remains consistent with the exclusion of payment processing. Users may agree to share travel costs, but the system does not handle financial transactions.
- CON-03: Remains consistent with the exclusion of real-time GPS tracking. Users manually provide pickup locations and destinations.
- CON-04: Remains consistent with the manual recurring schedule functionality, without integration with official UTD class schedules.

## Review Summary

All four constraint requirements remain applicable and consistent with the approved project scope.

The original requirement IDs (CON-01 through CON-04) and source references (S1, S2, R2) have been preserved. 
No changes to the requirements themselves are necessary.

The current architectural documentation supports these constraints. However, the wording of CON-01 in Section 6.1 requires clarification, 
and the completed Sections 6.4 and 9.1 should be checked for consistency during final review.

### Review Status: Reviewed & Updated

The documentation has been updated to record the review results and correct minor wording issues.
