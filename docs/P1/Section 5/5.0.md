# 5.0 Open Questions

| Unresolved Question | When an answer is needed | What is being assumed at the moment |
|---|---|---| 
| How will the system verify users are part of the UTD community? | Before account development begins | Only UTD community members will use the app | 
| What information must users provide when creating an account? | Before account development begins | Users will only register with a UTD email |
| What happens if a user forgets their password or wants to delete their account? | Before account development is completed | We will implement this 'obvious' feature as part of account management |
| What if an existing user is no longer part of the UTD community? | Before account development is completed | Their accounts should be automatically deactivated, but there is no resolution to implement this |
| Can users be both riders and drivers? | Before designing user roles | Users can be both riders and drivers | 
| Can a user be suspended or banned after multiple safety reports? | Before designing safety reports | We will not manually moderate the app after it has been released |
| What information must drivers provide when posting a ride? | Before designing the ride-posting feature | The drivers will provide their current location |
| Can drivers specify the number of available seats? | Before designing ride availability and matching | The drivers will manually have to disable their requests once they are full, or a driver will only be able to accept one rider |
| Can users edit a ride or request after posting it? | Before completing ride management | Users cannot edit rides or requests, only cancel |
| Will rides and requests automatically expire after their scheduled date and time? | Before implementing ride requests | No, they will have to be manually disabled |
| How will the system determine whether a ride matches a rider's request? | Before implementing matching logic | The system will pair nearby riders and drivers |
| Can riders filter results by date, time, pickup location, destination, and seats? | Before designing search functionality | We will implement this 'obvious' feature as part of the search function |
| What happens if multiple riders try to claim the same available seat? | Before implementing ride acceptance | There is currently no function to determine if a ride becomes full, or a driver will only be able to accept one rider |
| Can drivers accept or reject ride requests? | Before implementing request management | All requests will be automatically accepted |
| Can riders cancel after a driver has accepted their request? | Before implementing cancellation | Riders can cancel a request at any moment |
| Can drivers cancel after riders have been matched? | Before implementing cancellation | Drivers can cancel a request at any moment | 
| Will the app notify users about ride acceptances, cancellations, messages, and other important information? | Before finalizing the app structure | There is no resolution to implement notifications |
| What happens if a driver or rider does not show up to their agreed location? | Before implementing safety reports and cancellation features | Users should cancel their requests and report inappropriate behavior |
| What communication features will in-app messaging support? | Before designing the messaging feature | Only text will be supported |
| How will riders and drivers agree on travel contributions? | Before implementing ride details and coordination | The riders and drivers will privately decide on the contribution |
| Can drivers suggest a contribution amount when posting a ride? | Before finalizing ride-posting details | There is no resolution to implement this. Drivers will manually have to communicate through the app or in person |
| Will agreed contribution amounts be saved in ride details? | Before finalizing ride details | No, drivers will need to log their contribution amounts elsewhere |
| How will the app communicate that contributions are voluntary and unenforced? | Before designing the user interface | Users can choose not to contribute, but perhaps this will be noted in a disclaimer |
| Which profile details will be visible to other students? | Before designing user profiles | Only their username and location should be visible |
