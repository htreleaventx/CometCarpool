## Repository Structure

The repository contains the following directories for P2:

- `docs/P1/` — P1 requirements specification.
- `docs/P2/` — P2 documentation and analysis artifacts. Section files are in `docs/P2/P2 Sections/`, open-question answers are in `docs/P2/Open Questions/`, and planning documents are in `docs/P2/Plan To P2/`.
- `docs/P2/P2 Sections/diagrams/` — Diagram source files (Mermaid `.mmd`) and exported images (`.png`).
- `docs/Git_Workflow.md` — The team's Git and pull request procedure.
- `src/backend/` — Backend application (Java 21, Spring Boot, Maven).
- `src/frontend/` — Frontend application (React, TypeScript). Created when frontend development begins.
- `spikes/` — Architecture spike implementations and evidence. Created when the spike is committed.
- `setup/` — Scripts that install the development tools on macOS and Windows.
- `.github/CODEOWNERS` — Assigns the Project Manager as the code owner for the whole repository.

## Branch and Pull Request Workflow

The full procedure is documented in `docs/Git_Workflow.md`.

### Branch Creation

Team members create branches for assigned tasks rather than making changes directly to the protected main branch. A branch is created from the latest `main` and focuses on one feature, fix, or documentation task. Branch names use a prefix that describes the work: `feature/`, `bugfix/`, `docs/`, `refactor/`, or `test/` (for example, `docs/p2-5.2-object-interaction`).

### Pull Requests

Changes are submitted through pull requests for review before being merged into main. This applies to documentation changes as well as code. The pull request title and description explain what changed and which issues it addresses. Team members may open pull requests but do not merge their own.

### Review and Approval

The main branch has a repository ruleset configured with the following requirements:

- Changes must be made through a pull request.
- At least one approving review is required.
- Review from a code owner is required. The Project Manager is the code owner of the whole repository.
- The most recent push to a pull request must be approved by someone other than the person who pushed it.
- Earlier approvals are dismissed when new commits are pushed.
- All review conversations must be resolved before merging.
- The main branch cannot be deleted, and force pushes to it are blocked.

The Project Manager reviews the changed files, confirms they match the assigned task, and approves the pull request once requested corrections are made on the same branch.

### Merge Process

Approved pull requests are merged into main by the Project Manager using a merge commit. The ruleset allows only the merge method, and squash merging is not used. This keeps each team member's individual commits visible in the Git history for contribution documentation. After a pull request is merged, its branch can be deleted without losing any commit history.

## P2 Baseline

The P2 baseline will be identified using the Git tag:

`p2`

The tag must reference the commit containing the exact final P2 PDF submitted for grading. It is created after the final P2 PDF is committed to main, using:

```bash
git tag p2 <commit-containing-final-pdf>
git push origin p2
```
