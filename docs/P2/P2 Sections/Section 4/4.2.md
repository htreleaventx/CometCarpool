# 4.2 Expanded Use Cases

## Overview

This section expands the selected use cases into detailed actor-system interactions.

Each use case describes the actions performed by the actor, the corresponding system responses, and any alternate flows.

The descriptions remain technology-independent and focus on observable system behavior.

---

## UC-03 — Search and Manage Ride Requests

### Use Case Information

| Field | Description |
| :--- | :--- |
| Use Case ID   | UC-03 |
| Use Case Name | Search and Manage Ride Requests |
| Primary Actor | Student Rider |
| Supporting Actors and External Systems | Student Driver |
| TUCBW (This Use Case Begins When) |  THe student rider opens the ride search feature to find transportation. |
| TUCEW (This Use Case Ends When) | The student rider successfully posts a ride request and recieves information. |
| Preconditions | The student rider has an active, verified cometcarpool account and is also logged into the system. |
| Postconditions | the ride request is saved and visible to eligible drivers. |
| Traces to Requirements | FR-04, FR-05, FR-06, FR-11, QR-01, QR-03, QR-04, QR-05; CON-01. |

### Main Success Scenario

| Actor Input / Action | System Response |
| :--- | :--- |
|  | (0) The system displays the ride search interface with options to search for rides and manage existing requests. |
| (1) The Student Rider enters the desired pickup location, destination, date, and time. |  |
|  | (2) The system displays available rides matching the search criteria. |
| (3) The Student Rider reviews the search results and selects the option to create a new ride request. |  |
|  | (4) The system displays the ride request form. |
| (5) The Student Rider enters the pickup location, destination, date, and time, then submits the request. |  |
|  | (6) The system validates the submitted trip details. |
|  | (7) The system records the ride request and makes it available to eligible drivers. |
|  | (8) The system displays confirmation that the request was posted successfully. |

### Alternate Flows

| Alternate Flow | At Step | Condition | What Happens | Ends or Rejoins At |
| :--- | :--- | :--- | :--- | :--- |
| 2a — No Matching Rides | (2) | No rides match the search criteria. | The system informs the rider that no matching rides were found and offers the option to create a ride request. | Rejoins at (3). |
| 6a — Missing Trip Information | (6) | Required trip details are missing. | The system identifies missing fields and asks the rider to complete them. The request is not posted. | Returns to (5). |
| 3a — Existing Ride Selected | (3) | The rider selects an existing available ride. | The system displays the selected ride details and provides an option to coordinate the ride. | Continues with UC-05. |
| 0a — Cancel Existing Request | (0) | The rider wants to cancel a previously posted request. | The rider selects an existing request and confirms cancellation. The system marks it as canceled, removes it from available requests, and displays confirmation. | Ends UC-03. |

### Requirements Traceability

List the functional requirements, quality requirements, and constraints associated with this use case.

- Functional Requirements:
    - FR-04: Allow riders to post ride requests
    - FR-05: Allow users to enter pickup location, destination, date, and time. 
    - FR-06: Allow users to search available rides and ride requests. 
    - FR-11: Allow users to cancel posted rides or ride requests 
- Quality Requirements:
    - QR-01: At least 95% of ride searches return results within 2 seconds under normal load of up to 50 concurrent users. 
    - QR-03: At least 99% of valid save operations succeed during normal operation 
    - QR-04: New users can post a ride or ride request within 3 minutes without assistance after logging in. 
    -QR-05: authentication is required before accessing protected infromation and features

- Constraints:
    - CON-01: system access is restricted to members of the UTD community.

## UC-04 — Manage Recurring Schedules and Find Matches

### Use Case Information

| Field | Description |
| :--- | :--- |
| Use Case ID | UC-04 |
| Use Case Name | Manage Recurring Schedules and Find Matches |
| Primary Actor | Student Rider |
| Supporting Actors and External Systems | Student Driver |
| TUCBW (This Use Case Begins When) | The Student Rider opens the recurring schedule feature to record their weekly transportation needs and find compatible drivers. |
| TUCEW (This Use Case Ends When) | The Student Rider saves their recurring schedule and reviews the potential matches identified by the system. |
| Preconditions | The Student Rider has an active, verified CometCarpool account and is logged into the system. Driver schedules may already be stored for matching. |
| Postconditions | The Student Rider's recurring transportation schedule is saved. The system has displayed any compatible driver schedules. No ride is automatically confirmed. |
| Traces to Requirements | FR-07, FR-08, FR-09; QR-03, QR-05; CON-01, CON-04 |

### Main Success Scenario

| Actor Input / Action | System Response |
| :--- | :--- |
|  | (0) The system displays the recurring schedule interface. |
| (1) The Student Rider selects the days of the week they regularly need transportation. |  |
|  | (2) The system displays the selected days and available time fields. |
| (3) The Student Rider enters the times they regularly need transportation. |  |
|  | (4) The system displays the completed schedule for review. |
| (5) The Student Rider submits the recurring schedule. |  |
|  | (6) The system validates the entered information. |
|  | (7) The system saves the recurring schedule. |
|  | (8) The system displays confirmation that the schedule was saved. |
| (9) The Student Rider selects the option to find compatible schedules. |  |
|  | (10) The system compares the rider's schedule with driver availability. |
|  | (11) The system displays potential matches. |
| (12) The Student Rider reviews the matches and selects a potential driver. |  |
|  | (13) The system displays the selected driver's relevant ride information and an option to coordinate through UC-05. |


### Alternate Flows

| Alternate Flow | At Step | Condition | What Happens | Ends or Rejoins At |
| :--- | :--- | :--- | :--- | :--- |
| 11a — No Compatible Schedules | (11) | No compatible driver schedules are found. | The system informs the rider that no matches were found and offers the option to modify the schedule. | Returns to (1) if modified; otherwise ends. |
| 6a — Missing Schedule Information | (6) | Required days or times are missing. | The system identifies missing information and asks the rider to correct it. | Returns to (1) for missing days or (3) for missing times. |
| 0a — Update Existing Schedule | (0) | The rider wants to modify an existing schedule. | The system displays the existing schedule for editing. | Continues at (1). |
| 13a — Matching Driver Unavailable | (13) | The selected driver is no longer available. | The system informs the rider and allows them to select another available match. | Returns to (12) if other matches exist; otherwise ends. |

### Requirements Traceability

- **Functional Requirements:**
  - FR-07: The system allows drivers to record the days and times they are regularly available to drive.
  - FR-08: The system allows riders to record the days and times they regularly need transportation.
  - FR-09: The system allows users to identify riders or drivers with compatible recurring schedules.

- **Quality Requirements:**
  - QR-03: At least 99% of valid recurring schedule updates must be saved successfully during normal operation.
  - QR-05: Authentication is required before accessing protected recurring schedule information.

- **Constraints:**
  - CON-01: Account creation and system access are restricted to members of the UTD community.
  - CON-04: The system must not automatically import a student's official class schedule.

## UC-02 — Post and Manage Ride Offers

### Use Case Information

| Field | Description |
| :--- | :--- |
| Use Case ID | UC-02 |
| Use Case Name | Post and Manage Ride Offers |
| Primary Actor | Student Driver |
| Supporting Actors and External Systems | Student Rider. No external systems are required. |
| TUCBW (This Use Case Begins When) | The Student Driver opens the ride posting feature to offer transportation to other students. |
| TUCEW (This Use Case Ends When) | The Student Driver successfully posts a ride offer and receives confirmation that it is available to eligible riders. |
| Preconditions | The Student Driver has an active, verified CometCarpool account and is logged into the system. |
| Postconditions | The ride offer is saved and visible to eligible riders, including its trip details and available passenger seats. |
| Traces to Requirements | FR-03, FR-05, FR-11, FR-15; QR-03, QR-04, QR-05; CON-01 |

### Main Success Scenario

| Actor Input / Action | System Response |
| :--- | :--- |
|  | (0) The system displays the ride management interface with options to create or manage ride offers. |
| (1) The Student Driver selects the option to post a new ride. |  |
|  | (2) The system displays a ride posting form. |
| (3) The Student Driver enters the pickup location, destination, departure date, and time. |  |
|  | (4) The system displays the entered trip details for review. |
| (5) The Student Driver specifies the number of available passenger seats. |  |
|  | (6) The system displays the available seat count in the ride details. |
| (7) The Student Driver reviews the information and submits the ride offer. |  |
|  | (8) The system confirms that the ride offer has been recorded and is available to eligible riders. |

### Alternate Flows

| Alternate Flow | At Step | Condition | What Happens | Ends or Rejoins At |
| :--- | :--- | :--- | :--- | :--- |
| A1 - Missing Trip Information | (8) | The driver submits a ride offer without required trip information. | The system identifies missing fields and asks the driver to complete them before saving. | Returns to Step (3). |
| A2 - Invalid Seat Count | (8) | The driver enters an invalid number of available passenger seats. | The system rejects the invalid value and asks the driver to enter a valid number. | Returns to Step (5). |
| A3 - Update Existing Ride | (0) | The driver wants to modify a ride they previously posted. | The driver selects an existing ride and may update its details before the ride is confirmed. Once confirmed, unilateral changes are not allowed. | Ends when the system confirms the update. |
| A4 - Cancel Ride Offer | (0) | The driver chooses to cancel an existing ride offer. | The system displays the selected ride and asks for confirmation. After confirmation, it marks the ride as canceled and removes it from available ride listings. | Ends when the cancellation is confirmed. |
| A5 - Driver Cancels Posting | (7) | The driver decides not to publish the ride offer. | The driver chooses to cancel instead of submitting. The system returns to the ride management interface without creating a ride offer. | Ends the use case without creating a ride offer. |

### Requirements Traceability

- **Functional Requirements:**
  - FR-03: The system allows drivers to post available rides.
  - FR-05: The system allows users to include pickup location, destination, date, and time in ride postings.
  - FR-11: The system allows users to cancel posted rides or ride requests.
  - FR-15: The system allows rides with destinations on the UTD campus and in surrounding Dallas areas.

- **Quality Requirements:**
  - QR-03: At least 99% of valid ride postings and updates must be saved successfully during normal operation.
  - QR-04: A new user must be able to post a ride within 3 minutes without assistance after logging in.
  - QR-05: Authentication is required before accessing protected account information and features.

- **Constraints:**
  - CON-01: Account creation and system access are restricted to members of the UTD community.
