# 4.2 Expanded Use Cases

## Overview

This section expands the selected use cases into detailed actor-system interactions.

Each use case describes the actions performed by the actor, the corresponding system responses, and any alternate flows.

The descriptions remain technology-independent and focus on observable system behavior.

---

## UC-03 — Search and Manage Ride Requests

### Use Case Information

| Field | Description |
| :--- | :--- |
| Use Case ID   | UC-03 |
| Use Case Name | Search and Manage Ride Requests |
| Primary Actor | Student Rider |
| Supporting Actors and External Systems | Student Driver |
| TUCBW (This Use Case Begins When) |  THe student rider opens the ride search feature to find transportation. |
| TUCEW (This Use Case Ends When) | The student rider successfully posts a ride request and recieves information. |
| Preconditions | The student rider has an active, verified cometcarpool account and is also logged into the system. |
| Postconditions | the ride request is saved and visible to eligible drivers. |
| Traces to Requirements | FR-04, FR-05, FR-06, FR-11, QR-05, CON-01. |

### Main Success Scenario

| Actor Input / Action | System Response |
| :--- | :--- |
| | (0) The system displays the ride search interface. |

| (1) The student rider enters their desired pickup location, destination, date, and time. | (2) The system searches for available rides matching the entered criteria and displays the results. |

| (3) The Student Rider reviews the available rides and chooses to create a new ride request| (4) System displays the ride request form. |

| (5) The student rider enters the required trip details and submits a ride request. | (6) The system validates the information and saves the ride request. |

| (7) the student rider views the submitted request | (8) The system displays confirmation that the request was posted and is available for elligible drivers to view. |

### Alternate Flows

| Alternate Flow | At Step | Condition | What Happens | Ends or Rejoins At |
| :--- | :--- | :--- | :--- | :--- |
| A1 - No Matching Rides | (2) | No available rides match the Student Rider's search criteria. | The system informs the rider that no matching rides were found. The rider may choose to create a new ride request instead. | Rejoins at Step (3). |
| A2 - Missing Trip Information | (6) | The Student Rider submits a ride request without all required trip details. | The system identifies the missing information and asks the rider to complete the required fields before submitting again. | Returns to Step (5). |
| A3 - Existing Ride Selected | (3) | The Student Rider finds an available ride and chooses it instead of posting a new request. | The system displays the selected ride information, allowing the rider to proceed with ride coordination. | Ends UC-03 and proceeds to UC-05. |
| A4 - Request Cancellation | After (8) | The Student Rider decides to cancel a previously posted ride request. | The system marks the request as canceled and removes it from the available ride requests. | Ends the cancellation flow. 

### Requirements Traceability

List the functional requirements, quality requirements, and constraints associated with this use case.

- Functional Requirements:
    - FR-04: Allow riders to post ride requests
    - FR-05: Allow users to enter pickup location, destination, date, and time. 
    - FR-06: Allow users to search available rides and ride requests. 
    - FR-11: Allow users to cancel posted rides or ride requests 
- Quality Requirements:
    - QR-01: At least 95% of ride searches return results within 2 seconds under normal load of up to 50 concurrent users. 
    - QR-03: At least 99% of valid save operations succeed during normal operation 
    - QR-04: New users can post a ride or ride request within 3 minutes without assistance after logging in. 
    -QR-05: authentication is required before accessing protected infromation and features

- Constraints:
    - CON-01: system access is restricted to members of the UTD community.

## UC-04 — Manage Recurring Schedules and Find Matches

### Use Case Information

| Field | Description |
| :--- | :--- |
| Use Case ID | UC-04 |
| Use Case Name | Manage Recurring Schedules and Find Matches |
| Primary Actor | Student Rider |
| Supporting Actors and External Systems | Student Driver |
| TUCBW (This Use Case Begins When) | The Student Rider opens the recurring schedule feature to record their weekly transportation needs and find compatible drivers. |
| TUCEW (This Use Case Ends When) | The Student Rider saves their recurring schedule and reviews the potential matches identified by the system. |
| Preconditions | The Student Rider has an active, verified CometCarpool account and is logged into the system. Driver schedules may already be stored for matching. |
| Postconditions | The Student Rider's recurring transportation schedule is saved. The system has displayed any compatible driver schedules. No ride is automatically confirmed. |
| Traces to Requirements | FR-07, FR-08, FR-09; QR-03, QR-05; CON-01, CON-04 |

### Main Success Scenario

| Actor Input / Action | System Response |
| :--- | :--- |
| | (0) the system displays the recurring schedule interface with operations to enter the transportation needs and search for compatible schedules. |
| (1) The Student Rider selects the days of the week they regularly need transportation. | (2) The system records the selected days and displays the available time fields. |
| (3) The Student Rider enters the times they regularly need transportation. | (4) The system displays the completed recurring schedule for review. |
| (5) The Student Rider selects the option to save their recurring schedule. | (6) The system validates and saves the schedule, then displays confirmation. |
| (7) The Student Rider selects the option to find compatible schedules. | (8) The system compares the rider's recurring transportation needs with saved driver availability and displays potential matches. |
| (9) The Student Rider reviews the compatible driver schedules and selects a potential driver. | (10) The system displays the selected driver's relevant ride information and provides an option to coordinate the ride through UC-05. |


### Alternate Flows

| Alternate Flow | At Step | Condition | What Happens | Ends or Rejoins At |
| :--- | :--- | :--- | :--- | :--- |
| A1 - No Compatible Schedules | (8) | No driver schedules match the rider's selected days and times. | The system informs the rider that no compatible schedules were found. The rider may change their schedule or check again later. | Returns to Step (1) if the rider changes their schedule; otherwise ends the use case. |
| A2 - Missing Schedule Information | (6) | The rider attempts to save a schedule without the required days or times. | The system identifies the missing information and asks the rider to complete it. The incomplete schedule is not saved. | Returns to Step (3) or Step (5), depending on the missing information. |
| A3 - Driver Saves Availability | (0) | A Student Driver opens the recurring schedule feature instead of a Student Rider. | The driver selects the days and times they are regularly available to offer rides. The system validates and saves the driver's recurring availability for future matching. | Ends when the driver receives confirmation that their availability was saved. |
| A4 - Update Existing Schedule | (0) | The Student Rider already has a recurring transportation schedule and wants to modify it. | The system displays the existing schedule. The rider edits the days or times and saves the changes. The system stores the updated schedule. | Rejoins at Step (7) if the rider wants to search for matches; otherwise ends. |
| A5 - Matching Driver Unavailable | (9) | A previously identified driver is no longer available for the desired schedule. | The system informs the rider that the selected driver is unavailable and allows them to review other potential matches. | Returns to Step (8), if other matches exist; otherwise ends. |

### Requirements Traceability

- **Functional Requirements:**
  - FR-07: The system allows drivers to record the days and times they are regularly available to drive.
  - FR-08: The system allows riders to record the days and times they regularly need transportation.
  - FR-09: The system allows users to identify riders or drivers with compatible recurring schedules.

- **Quality Requirements:**
  - QR-03: At least 99% of valid recurring schedule updates must be saved successfully during normal operation.
  - QR-05: Authentication is required before accessing protected recurring schedule information.

- **Constraints:**
  - CON-01: Account creation and system access are restricted to members of the UTD community.
  - CON-04: The system must not automatically import a student's official class schedule.

## UC-02 — Post and Manage Ride Offers

### Use Case Information

| Field | Description |
| :--- | :--- |
| Use Case ID | UC-02 |
| Use Case Name | Post and Manage Ride Offers |
| Primary Actor | Student Driver |
| Supporting Actors and External Systems | Student Rider. No external systems are required. |
| TUCBW (This Use Case Begins When) | The Student Driver opens the ride posting feature to offer transportation to other students. |
| TUCEW (This Use Case Ends When) | The Student Driver successfully posts a ride offer and receives confirmation that it is available to eligible riders. |
| Preconditions | The Student Driver has an active, verified CometCarpool account and is logged into the system. |
| Postconditions | The ride offer is saved and visible to eligible riders, including its trip details and available passenger seats. |
| Traces to Requirements | FR-03, FR-05, FR-11, FR-15; QR-03, QR-04, QR-05; CON-01 |

### Main Success Scenario

| Actor Input / Action | System Response |
| :--- | :--- |
| | (0) The system displays the ride management interface with an option to create a new ride offer. |
| (1) The Student Driver selects the option to post a new ride. | (2) The system displays a ride posting form. |
| (3) The Student Driver enters the pickup location, destination, departure date, and time. | (4) The system records the entered trip details and displays them for review. |
| (5) The Student Driver specifies the number of available passenger seats. | (6) The system records the available seat count and includes it in the ride details. |
| (7) The Student Driver reviews the information and submits the ride offer. | (8) The system validates the required information and saves the ride offer. |
| (9) The Student Driver views the completed posting. | (10) The system confirms that the ride is available and displays it to eligible riders. |

### Alternate Flows

| Alternate Flow | At Step | Condition | What Happens | Ends or Rejoins At |
| :--- | :--- | :--- | :--- | :--- |
| A1 - Missing Trip Information | (8) | The driver submits a ride offer without required trip information. | The system identifies missing fields and asks the driver to complete them before saving. | Returns to Step (3). |
| A2 - Invalid Seat Count | (8) | The driver enters an invalid number of available passenger seats. | The system rejects the invalid value and asks the driver to enter a valid number. | Returns to Step (5). |
| A3 - Update Existing Ride | (0) | The driver wants to modify a ride they previously posted. | The system displays the driver's existing ride offers. The driver selects a ride, changes permitted details, and saves the updated posting. | Ends when the system confirms the update. |
| A4 - Cancel Ride Offer | (0) | The driver chooses to cancel an existing ride offer. | The system displays the selected ride and asks for confirmation. After confirmation, it marks the ride as canceled and removes it from available ride listings. | Ends when the cancellation is confirmed. |
| A5 - Seat Availability Changes | After (10) | A rider is accepted or an accepted rider cancels their participation. | The system updates the remaining available seats to reflect the change. | Ends when the updated seat count is saved. |
| A6 - Driver Cancels Posting | (7) | The driver decides not to publish the ride offer. | The system returns the driver to the ride management interface without publishing the new ride. | Ends the use case without creating a ride offer. |

### Requirements Traceability

- **Functional Requirements:**
  - FR-03: The system allows drivers to post available rides.
  - FR-05: The system allows users to include pickup location, destination, date, and time in ride postings.
  - FR-11: The system allows users to cancel posted rides or ride requests.
  - FR-15: The system allows rides with destinations on the UTD campus and in surrounding Dallas areas.

- **Quality Requirements:**
  - QR-03: At least 99% of valid ride postings and updates must be saved successfully during normal operation.
  - QR-04: A new user must be able to post a ride within 3 minutes without assistance after logging in.
  - QR-05: Authentication is required before accessing protected account information and features.

- **Constraints:**
  - CON-01: Account creation and system access are restricted to members of the UTD community.
