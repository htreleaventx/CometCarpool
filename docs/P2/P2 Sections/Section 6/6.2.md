# 6.2 Architectural Style and Alternatives

## Overview

This section compares architectural styles considered for the Comet Carpool System and identifies the architecture selected for development.

The comparison considers how each style supports the quality-attribute scenarios in Section 6.1 and the technical constraints of the project.

At least three architectural approaches must be considered, including the selected architecture and two rejected alternatives.

## Architectural Style Comparison

| Style Considered | Drivers It Serves | What It Costs | Verdict |
| :--- | :--- | :--- | :--- |
| Layered (N-Tier) | It separates the React/TypeScript frontend, Spring Boot backend and PostgreSQL database. Supports: QAS-01/03/04/05/06 through defined responsibilities. | Changes affecting multiple layers require coordination. The centralized backend could become a potential performance bottleneck as our number of users increases. | Chosen |
| Client-Server | Allows React client to request services from the Spring Boot backend while keeping application state and database access centralized. Supports: QAS-01/05 | Centralized server can become a single point of failure because the client depends on the network connectivity. Doesn't independently organize our backend into separate layers. | Rejected |
| Model-View-Controller | Separates application state, presentation, and input handling. Supports: QAS-04/05/06 through separation of responsibilities. | Adds organizational overhead for more simpler interactions. The business logic may become mixed into controllers if responsibilities aren't maintained. | Rejected |
| Repository | Allows components to share information through a central data store. Can support consistency for ride info, messages, and user accounts with QAS-03 | The shared repository could become a single point for failure and changes to its schema could effect every dependent component. | Rejected |
| Event-Driven | Allows components to publish and subscribe to events without directly calling each other. May support QAS-02 and ride request notifications | Rejected |

## Summary 

Comet Carpool will use a Layered (N-Tier) Architecture to separate presentation, data storage and application logic. This approach best supports security by keeping authentication and protected information in the backend, reliability through controlled database access and performance through organized request processing. The selected tech stack (see [CometCarpool_Final_Tech_Stack.md](https://github.com/htreleaventx/CometCarpool/blob/main/docs/P2/Plan%20To%20P2/CometCarpool_Final_Tech_Stack.md)) would fit this layered structure the best. Although an Event-Drive approach would offer great flexibility in scaling and asynchronous communication it would introduce additional complexity. We have come to terms with additional processing between layers and coordination across the components in exchange for a more simpler/maintainable architecture.
