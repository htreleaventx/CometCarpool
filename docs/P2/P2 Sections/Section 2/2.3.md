# 2.3 User characteristics

**Student drivers** - university students who have access to a vehicle and are willing to offer available seats to other students. They are expected to have basic experience using common web or mobile applications, but the system does not require advanced technical knowledge. Drivers may access the system from either a smartphone or a computer and may need to create or update ride information quickly before traveling. Therefore, the interface should make common actions easy to understand and complete.

**Student passengers** - university students who are looking for transportation to or from campus or other agreed destinations. They are expected to be familiar with basic web or mobile applications, but they should not need advanced technical knowledge to use the system. Passengers may often use the system from a smartphone and may need to find a suitable ride quickly based on location, date, and departure time. Ride information and request status should therefore be presented clearly.

**System administrators** - users responsible for basic system management and moderation. They are expected to have a higher level of familiarity with the application than regular users, but they should not need programming or database knowledge to perform administrative tasks. Administrators are more likely to use the system from desktop or laptop computer when reviewing user accounts, reports, or other system information.

### Consistency with Use-Case Actors

- The use cases expanded in Section 4.2 (UC-03 and UC-04) use Student Rider as the primary actor and Student Driver as the supporting actor. These match the passenger and driver groups above. The terms "passenger" and "rider" refer to the same group.
- The system administrator is not an actor in any expanded use case in Section 4.2.

### Observations for the Team

1. **One account, two roles (Q5).** Q5 decided that a single account can act as both a driver and a rider. The driver and passenger descriptions remain accurate as descriptions of how a student behaves when offering or requesting a ride, but a reader could assume they are separate kinds of users. A clarifying sentence could be added if the team agrees.
2. **Administrator role (Q6).** Q6 decided that the team will not actively moderate the system, and that suspension and banning happen automatically. The description of administrators who review user accounts and reports on a desktop computer does not match this approach. The same question is raised for stakeholder S3 in Section 2.2. The team should decide what administrators do, if anything, in the first version of the system.
