# 6.6 Design Principles Applied

## Overview

This section identifies how established software design principles are applied to the Comet Carpool architecture.

Each principle should be supported by specific evidence from the architectural components, interfaces, or architectural decision records.

## Design Principles

| Principle | Where It Shows in Your Design | Evidence (Component, Interface, ADR) |
| :--- | :--- | :--- |
| Separation of Concerns | Layered (N-Tier) architecture separates the UI, application logic, domain model, and data storage into distinct layers | Web Application, API Controller, Domain Model, Carpool Repository, Section 6.2 |
| Information Hiding | Backend services access stored information through the RepositoryAccess interface rather than interacting directly with the PostgreSQL database | Carpool Repository, RepositoryAccess |
| Low Coupling | Components communicate through defined interfaces, reducing dependencies on the internal implementation of other components | CarpoolAPI, AuthAPI, RideAPI, RequestAPI, MessageAPI, ReviewAPI |
| High Cohesion | Each backend service focuses on specific responsibilities such as authentication, ride management, messaging or reviews | Authentication Service, Ride Management Service, Messaging Service, Review and Reporting Service | 
| Design for Change | Separating services allows individual features to be modified without requiring changes to unrelated components | Ride Management Service, Messaging Service, Review & Reporting Service, Section 6.2 |
| Keep It Simple (KISS) | The system uses a straight forward Layered (N-Tier) architecture instead of introducing the additional complexity of an event driven architecture | Section 6.2 |
